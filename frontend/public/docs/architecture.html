Architecture overview

The demo helps a supervisor review building records without assembling the sources, definitions, and guidance by hand.

Strategy-first data path

Diagram summary

The served page uses the plain-language flow above instead of a runtime Mermaid block.

ADLS Gen2 is built on Blob Storage and provides a hierarchical namespace. Strategy imports CSV files through its Azure Data Lake Storage Gen2 file-storage connector. Strategy owns the relationships, attributes, measures, and hierarchies.

Why these parts are separate

The Azure ingestion job reads each source at its original grain. It writes:

  • complaint problems;
  • candidate violations;
  • supporting 311 requests;
  • a building-level summary; and
  • a process manifest.

Strategy maps building_id and creates the business view. The app reads the process manifest and the approved review result. It does not access raw Blob Storage data from the browser.

Refresh

The file layout keeps stable current paths, one Strategy folder per table, and immutable dated archives. Strategy's Daily refresh replaces data from the strategy-* folders. The archive preserves the evidence for each run.

Current status

The deployment creates an ADLS Gen2 account and the heat-hot-water container. Resource names stay in the authorized Azure deployment. Current files and a dated archive are present.

The app uses managed identity. Shared-key storage authentication is disabled in the public Bicep deployment. Any external Strategy connection is configured outside this repository.

Data flow

1. Read public sources

The Azure ingestion process reads:

  • HPD complaints and problems;
  • HPD housing-code violation candidates; and
  • NYC 311 heat and hot-water requests.

The allowlist excludes apartments, addresses, coordinates, person fields, owner details, and 311 resolution text.

2. Preserve source grain

The process writes separate current files:

PathGrain
current/complaint-problems.csvOne problem record
current/violation-candidates.csvOne candidate violation
current/requests-311.csvOne 311 request
current/building-review.csvOne building
current/manifest.jsonOne ingestion run

The same CSVs are copied to one-file Strategy folders: strategy-buildings/, strategy-complaints/, strategy-violations/, and strategy-requests-311/. This layout meets Strategy's requirement that a folder share one file type and schema.

The same files are copied under archive/YYYY-MM-DD/.

3. Create building facts

The building summary counts distinct complaint_id, not problem rows. Violation text search creates candidates only. The process does not join one complaint to one violation.

Every candidate uses needs_review and every review state uses needs_verification until a qualified owner approves the rule.

4. Import into Strategy

Strategy's Azure Data Lake Storage Gen2 connector reads the stable current files. The Mosaic model maps building_id across the source tables.

The intended hierarchy is:

  • Borough;
  • Building; and
  • source facts such as Complaint, Candidate Violation, and 311 Request.

5. Refresh and present

Strategy schedules the Mosaic import refresh. The dashboard and review service must use the same rule_version and source window. If the manifest is stale or incomplete, the app must show a degraded state.

6. Prepare a cited briefing

The public app sends the governed Strategy metrics, synthetic practice record, and allowed citations to the hpd-review-agent.

The agent explains:

  • what the Strategy metric shows;
  • what remains unknown;
  • which source and official HPD guidance to verify; and
  • a possible staff follow-up.

The agent cannot issue a violation, contact a resident, recalculate a Strategy metric, or choose a legal action. In local Practice mode, a deterministic provider returns the same shape without calling a paid model.

7. Staff review

A housing staff member checks the evidence and makes the official decision outside the demo. The review list is not a legal or emergency-response queue.

Foundry briefing

The hpd-review-agent is a code-deployed hosted agent. It uses the Responses protocol and the configured gpt-5.4-mini deployment.

Strategy Mosaic remains the source of metric definitions. The agent cannot recalculate a Strategy metric. It can explain the supplied evidence, unknowns, suggested follow-up, and linked HPD guidance.

The deployed demo calls hpd-review-agent through FOUNDRY_AGENT_ENDPOINT. Local tests use the deterministic Practice provider. That fallback is visible in the user interface and never pretends to be a live model response.

The agent is deployed as an active hosted agent version and the public app is authorized with the Foundry Agent Consumer role. The agent identity has the separate Cognitive Services OpenAI User role needed to call the model.

ADLS controls

  • Hierarchical namespace is enabled.
  • Anonymous blob access is disabled.
  • Shared storage key access is disabled.
  • The app and developer receive Storage Blob Data Contributor only where they

need to write.

  • External Strategy connector credentials are configured outside the repository.
